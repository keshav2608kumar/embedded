P9: 1  System recap
P10: The Smart Parking Management System uses one CCTV/USB/IP camera to observe four fixed parking bays (S1–S4). A PC runs OpenCV and a YOLO vehicle detector, maps detections to calibrated slot polygons, and applies temporal filtering before publishing confirmed occupancy to an ESP32. The ESP32 displays availability on a 16×2 I²C LCD, operates a buzzer, and controls a servo-operated entrance gate using a finite-state machine (FSM). A separate vehicle-present sensor provides gate-passage safety; the watchdog timer (WDT) is intended to recover from an unresponsive firmware task. The system is designed for a small controlled parking demonstration. AI training, camera calibration and hardware timing values must be measured on the actual setup before performance claims are made.

P29: The design uses a Moore-style gate FSM for stable state-dependent outputs, with safety inputs evaluated as transition guards. A fault/safe state is included. The AI occupancy state is treated as input data to the gate controller, not as part of the gate FSM’s internal states.
P30: 3  System-behaviour FSM
P31: Model type: Moore-style FSM for gate outputs. Gate outputs (servo target, LCD gate status and buzzer pattern) are defined primarily by the current state. Input events and guards determine transitions. A safety override reopens the gate if the vehicle sensor detects a vehicle during closing.
P32: 3.1  Model type
P34: The system FSM covers CLOSED, OPENING, OPEN, VEHICLE_PASSING, CLOSING and FAULT_SAFE. Entry is permitted only when the latest valid occupancy packet reports at least one free slot and a vehicle request is present. If occupancy data becomes stale or communication fails, the controller must not rely indefinitely on stale availability; the implementation should inhibit new entry and raise an alert. The physical safe position must be confirmed with the actual gate mechanism and instructor.
P35: 3.2  State diagram
P36: Safe state: FAULT_SAFE. Stop issuing new opening/closing commands except a safety-controlled reopen if the vehicle sensor indicates an obstruction; command the mechanism to the configured safe target, inhibit new entry, show FAULT on the LCD and use a bounded buzzer alert. A watchdog reset must initialize outputs conservatively before accepting new commands. The exact mechanical safe action (hold-open versus closed) must be verified against the physical gate and obstruction risks; never force closing onto a vehicle.
P37: 3.3  State transition table
P38: Completeness rule: for unlisted events, the event is ignored and the current state is retained. Fault and obstruction events have priority over ordinary transitions. On the final firmware, enumerate all events explicitly and test every transition.
